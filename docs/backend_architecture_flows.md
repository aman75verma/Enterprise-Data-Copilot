# Backend Architecture & File Execution Flows

This document answers your questions about the backend files and provides end-to-end execution flows so you understand exactly how the system pieces together.

---

## Part 1: File Explanations

### 1. `logger.py` & `compare.py`
- **Where they are used:** `logger.py` is imported by `orchestrator.py` and `mcp_server.py`. It wraps every tool execution to calculate how many milliseconds the tool took and logs the arguments/results. `compare.py` is a standalone CLI script you run manually to test the latency difference between calling a tool directly vs over the network via MCP.
- **What they print:** The logger prints timestamped lines to the terminal showing `[DIRECT]` or `[MCP]`, the tool name, arguments, latency in ms, and a truncated result preview.
- **How to use them on the Frontend:** The frontend can absolutely use these logs! Because `orchestrator.py` returns the `tool_calls` trace (including latency) in the `/chat` API response, and `/admin/logs` fetches all recent logs from the database, you can build a **"Developer Mode" toggle or dropdown** in the React UI. When activated, the user sees exactly what tools the AI used, what SQL it wrote, and how many milliseconds the database took to respond.

### 2. `conversation_store.py` & `pool.py`
- **`pool.py`:** Database connections are expensive to open. Instead of opening a new connection every time the AI runs a tool, `pool.py` creates a "pool" of 10 connections when the server starts. Tools borrow a connection, run their query, and return it. This is what makes the backend scale.
- **`conversation_store.py`:** This handles all the SQL `INSERT` and `SELECT` statements specifically for saving chat history. When a user sends a message, `main.py` calls this file to save the user turn, and then later saves the AI's response and tool latency into the `conversations` and `turns` tables.

### 3. `errors.py` & `demo_tools.py`
- **`errors.py`:** Contains a single standardized `ToolError` class. By standardizing errors, if a tool fails (e.g., bad SQL), the orchestrator doesn't crash; it catches the `ToolError` and passes the error text back to the LLM so the LLM can apologize or try again.
- **`demo_tools.py`:** An early testing script created before the FastAPI server existed. It allows you to run the Python tool functions (`query_customer_db`, etc.) directly from the command line without any LLMs or HTTP servers involved.

### 4. `models.py` & `main.py`
- **`models.py`:** Defines the strict Pydantic shapes of our JSON data. When the frontend sends a POST request, FastAPI uses this file to ensure the request contains a `message` string. If the frontend sends bad data, FastAPI rejects it automatically.
- **`main.py`:** The FastAPI application itself. It defines the API routes (`/chat`, `/health`, `/conversations`, `/admin/logs`), sets up CORS (so the React frontend can talk to it without security errors), and acts as the entry point that ties all the other files together.

### 5. Why are live issues not fake?
You asked: *"for a custom query by user we have sql db and supabase docs.. but what about live issues how can they be fake...."*
**They aren't fake!** The SQL database and users are purely synthetic (generated by `seed.py`). The documentation is a static snapshot cloned into our vector database. But the issue tracker tool (`github_issues.py`) makes **real-time HTTP requests to the actual GitHub API** for the `supabase/supabase` repository. 
If a user asks "Are there any open bugs regarding Auth?", the tool fetches the *actual, current open bugs* from GitHub. This demonstrates to a potential employer that the copilot seamlessly blends private synthetic data with real-time public APIs.

## Part 2: End-to-End Execution Flows

Here is exactly how a request travels through every file in the backend.

### Scenario A: A user asks a Database Question
**User asks:** *"How many users are on the enterprise plan?"*

1. **Frontend (React)**: Sends `POST /chat` with `{"message": "How many users..."}`.
2. **`main.py`**: Receives request. Validates it against `ChatRequest` in **`models.py`**.
3. **`main.py`**: Calls `create_conversation()` in **`conversation_store.py`** to generate a UUID.
4. **`main.py`**: Calls `save_turn()` in **`conversation_store.py`** to save the user's prompt to PostgreSQL.
5. **`main.py`**: Calls `run_agent()` in **`orchestrator.py`**.
6. **`orchestrator.py`**: Loads the AI persona from **`system_prompt.py`**. Loads tool schemas from **`tool_registry.py`**.
7. **`orchestrator.py`**: Sends the prompt and tool schemas to the **Groq API (Llama 3.3)**.
8. **Groq API**: Returns a `tool_calls` intent saying "I need to use `query_customer_db`".
9. **`orchestrator.py`**: Starts the timer via **`logger.py`** and executes `query_customer_db()` located in **`sql_tool.py`**.
10. **`sql_tool.py`**: Borrows a database connection from **`pool.py`**. Validates the query is a safe `SELECT`. Executes it. Returns the row count. Returns connection to pool.
11. **`logger.py`**: Stops the timer and prints the latency to the console.
12. **`orchestrator.py`**: Sends the DB row count back to the **Groq API**.
13. **Groq API**: Reads the DB result and generates the final English answer: *"There are 15 users on the enterprise plan."*
14. **`main.py`**: Calls `save_turn()` in **`conversation_store.py`** to save the AI's answer, tool trace, and latency to the database.
15. **`main.py`**: Returns the `ChatResponse` (defined in **`models.py`**) to the Frontend.

### Scenario B: A user asks a GitHub Issue Question
**User asks:** *"Are there any open bugs with Row Level Security?"*

1. **Frontend (React)**: Sends `POST /chat`.
2. **`main.py`**: Validates via **`models.py`**, saves user turn via **`conversation_store.py`**.
3. **`orchestrator.py`**: Sends prompt to **Groq API** with tools from **`tool_registry.py`**.
4. **Groq API**: Determines this isn't a DB question, it's a bug question. Returns intent to call `check_issue_tracker`.
5. **`orchestrator.py`**: Starts timer via **`logger.py`** and executes `check_issue_tracker()` in **`issue_tracker_tool.py`**.
6. **`issue_tracker_tool.py`**: Instantiates `LiveIssueTrackerClient` from **`github_issues.py`**.
7. **`github_issues.py`**: Makes a real HTTP REST call over the internet to `api.github.com/search/issues?q=repo:supabase/supabase is:issue open Row Level Security`.
8. **`github_issues.py`**: Parses the live GitHub JSON and returns it up the chain.
9. **`logger.py`**: Stops the timer and logs the HTTP latency.
10. **`orchestrator.py`**: Sends the live GitHub bug titles back to the **Groq API**.
11. **Groq API**: Reads the bug list and generates the final answer: *"Yes, there are currently 3 open bugs regarding RLS..."*
12. **`main.py`**: Saves the AI's response and tool trace via **`conversation_store.py`**.
13. **`main.py`**: Returns response to the Frontend.

---

### Scenario C: The Admin Dashboard
**Developer opens the "Admin Logs" page.**

1. **Frontend (React)**: Sends `GET /admin/logs`.
2. **`main.py`**: Receives request and calls `get_recent_logs()` in **`conversation_store.py`**.
3. **`conversation_store.py`**: Borrows connection from **`pool.py`**, runs `SELECT * FROM turns WHERE tool_calls IS NOT NULL`, and returns connection.
4. **`main.py`**: Validates the DB rows against `LogEntry` in **`models.py`**.
5. **`main.py`**: Returns JSON array to Frontend, populating the admin dashboard with latency charts and tool usage history.
